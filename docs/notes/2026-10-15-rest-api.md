# The MiniLang REST API: Build Notes

**Date:** 2026-10-15 · **Author:** Ronish Shrestha · **Branch:** `feat/rest-api` · **Previous notes:** [Showcase site](2026-10-14-showcase-site.md)

The project could already be used three ways: the CLI, the MCP server (for AI assistants) and the in-browser playground. All three are for **people or agents on one machine**. Today we added the way most real systems integrate: a **REST API over HTTP**, built with FastAPI, packaged with Docker and deployable to Render. These notes explain the design, the protection against abuse, and the trade-offs, which are what FDE and Solutions interviews ask about.

---

## 1. Why an API when the site already runs the compiler in the browser?

They solve different problems:

| | Browser (Pyodide) | REST API |
|---|---|---|
| Who calls it | A person on the website | Other programs: scripts, CI jobs, agents, a customer's backend |
| Who pays for the compute | The visitor's laptop | Our server |
| Security risk | Only the visitor's own browser tab | Strangers run code on our machine, so we need limits |
| Best for | A public demo | Integration |

> **Interview line:** "The public demo runs in the browser because it's free and safe for anonymous visitors. Programs call the REST API, which has validation and rate limiting. I'd choose based on who's calling and who pays for the compute."

## 2. Endpoints

| Method | Path | Returns |
|---|---|---|
| `GET` | `/health` | `{"status": "ok", "version": "1.0.0"}` |
| `POST` | `/v1/run` | `ok`, `output`, `errors` (with hints), `diagnostic` |
| `POST` | `/v1/check` | `ok`, `errors`, `diagnostic` (nothing runs) |
| `POST` | `/v1/compile` | tokens, AST, TAC, assembly, output, per-stage timings |
| `GET` | `/v1/spec` | the language spec as `text/markdown` |

Design choices:
- **`/v1/` prefix (versioning).** If the response shape ever has to change, `/v2/` can live next to `/v1/` so existing callers don't break. `/health` isn't versioned because it's for infrastructure, not for clients.
- **POST for run/check/compile.** The program goes in a JSON body, which has no URL length limit and isn't written to proxy logs the way query strings are.
- **A program error is a `200`, not a `400`.** The *request* succeeded: the server compiled the program and is reporting what it found. `ok: false` plus the errors is the answer the caller asked for. A `4xx` means the *request* was wrong (bad JSON, missing field, too big, too many requests). Mixing the two would make a client treat "your program has a typo" like "your API call is broken".
- **Interactive docs for free.** FastAPI generates an OpenAPI schema from the Pydantic models, and `/docs` renders it as Swagger UI where anyone can try the endpoints.

## 3. How the code is organized

```
minilang/service.py        shared operations: run_program, check_program, compile_program, language_spec
minilang/api/
  config.py                Settings from MINILANG_* environment variables (validated at startup)
  schemas.py               Pydantic request/response models (also the OpenAPI docs)
  ratelimit.py             token bucket + per-client limiter
  errors.py                one error format for every failure
  middleware.py            client IP, request ID, JSON log line, the 500 safety net
  guards.py                rate limit + streaming body limit, before the body is parsed
  routes.py                the endpoints (thin: validate, take a slot, call the service)
  app.py                   create_app(): wires everything together
```

**Thin routes, logic in a service layer.** The routes only validate input, take a concurrency slot and call `minilang.service`. The service layer is plain Python with no FastAPI in it, so it's easy to test and the MCP server can use the same code.

**An app factory (`create_app(settings)`).** Every test builds a fresh app with its own settings (for example a limit of 2 requests per minute to test the 429) without touching environment variables or global state.

## 4. Validation: three layers

1. **Body size, before parsing** (`guards.py`, `BodyLimitMiddleware`). A body can arrive two ways: with a `Content-Length` header that says its size up front, or **chunked** (`Transfer-Encoding: chunked`), where the size is unknown until the last chunk. The first version only checked `Content-Length`, so a chunked upload walked straight past it. Now:
   - a declared `Content-Length` over the limit is refused with `413` without reading a byte;
   - otherwise the middleware reads the body chunk by chunk, keeps a running total, and answers `413` **the moment** the total passes the limit, without reading the rest;
   - a body within the limit is handed to FastAPI through a new `receive` function that "replays" the bytes it already read.
   This is **pure ASGI** middleware (a class called with `scope, receive, send`) rather than `@app.middleware("http")`, because only at the ASGI level can you see the body arrive piece by piece and stop reading.
2. **Shape** (Pydantic). `source` must be a non-empty string of at most 20,000 characters. `extra="forbid"` turns a typo like `{"sorce": ...}` into a clear error instead of silently ignoring it. A number is not quietly converted to a string.
3. **Length setting** (`routes.py`). `MINILANG_MAX_SOURCE_CHARS` can **lower** the limit; the route checks it and answers `422`. It can't raise it above 20,000: the schema's `maxLength` would silently cap it, so `Settings` refuses such a value at startup. The simplest correct option: the docs show the real default, and a setting can only make it stricter.

Every failure uses the same format:

```json
{"error": {"code": "invalid_request", "message": "The request body is invalid.",
           "details": [{"field": "sorce", "message": "Extra inputs are not permitted"}]}}
```

`code` is stable and machine-readable (`invalid_request`, `payload_too_large`, `rate_limited`, `server_busy`, `not_found`, `internal_error`), so clients can branch on it.

**Unexpected errors (500).** An exception is logged in full on the server (with the request ID and the traceback), but the client only sees "Something went wrong on our side." **Internals never leak** (a test checks the response doesn't contain the exception text). Where the 500 is produced matters: a FastAPI handler for `Exception` runs in Starlette's *outermost* layer, outside CORS and our own middleware, so that 500 had no `Access-Control-Allow-Origin` (the browser hides it from the page's JavaScript), no `X-Request-ID` and no log line. Now our request middleware catches the exception itself, *inside* CORS, so the 500 looks like every other response.

## 5. Rate limiting: the token bucket

Each client IP gets a bucket that holds up to 30 tokens:
- each request **takes** one token;
- tokens **refill** continuously at 30 per minute (one every 2 seconds);
- an empty bucket means **429 Too Many Requests**, with `Retry-After: <seconds until the next token>`.

```
capacity 30 ─┐ a burst of 30 requests at once is fine
             │ then one request per 2 s on average
refill 0.5/s ┘ the bucket never holds more than 30
```

Why a token bucket instead of "count requests per minute" (a fixed window)? A fixed window allows a double burst at the boundary (30 requests at 0:59 and 30 more at 1:00). A token bucket smooths that out and stores only two numbers per client: tokens and the time it last refilled.

Details that matter:
- **Refuse before reading.** FastAPI parses the JSON body *before* it runs a route's dependencies, so a rate limit written as a dependency still paid for the parse of every throttled request. The check now lives in `RateLimitMiddleware` (`guards.py`), which runs before the body is touched. A test proves it: a throttled request with invalid JSON gets `429`, not `422`. Only `POST /v1/run`, `/v1/check` and `/v1/compile` are limited; `/health`, `/v1/spec`, `/docs` and `/openapi.json` are not.
- **Thread safety.** Endpoints run in a thread pool, so two requests can update the same bucket at once. A lock around "get the bucket and take a token" prevents lost updates.
- **Bounded memory.** An `OrderedDict` keeps at most 10,000 clients and forgets the least recently seen one (LRU), so an attacker rotating IPs can't make memory grow forever.
- **A fake clock in tests.** The limiter takes a `clock` function. Tests pass one they can advance by hand, so "wait 2 seconds and a token is back" runs instantly and exactly.
- **Response headers.** `X-RateLimit-Limit` and `X-RateLimit-Remaining` on every compiler response, so a client can slow down before it gets a 429.
- **Known limit: in memory means per process.** With several servers (or several uvicorn workers) each would count separately, and a restart resets the counts. That's why the Dockerfile runs `--workers 1`. The fix at scale is a shared store such as **Redis** (an atomic increment with an expiry).

### Which IP is "the client"? (X-Forwarded-For)

On Render every request arrives from Render's load balancer, so the socket address is the proxy's, and every visitor would share one bucket. Proxies solve this with `X-Forwarded-For`: each one **appends** the address it received the request from.

```
client sends:        X-Forwarded-For: 6.6.6.6          <- anything the client likes
Render appends:      X-Forwarded-For: 6.6.6.6, 203.0.113.7
                                       ^ fake    ^ written by Render: the real peer
```

The first version ran uvicorn with `--proxy-headers --forwarded-allow-ips='*'`, which takes the **leftmost** entry, the one the client wrote. Sending a new fake value with each request gave a fresh bucket each time: no rate limit at all.

The fix is to count from the **right**, only as far as proxies we control:
- `MINILANG_TRUSTED_PROXY_HOPS=0` (default): ignore the header, use the socket peer. Right when nothing sits in front of the app.
- `=1`: take the 1st entry from the right (what our one proxy appended). `render.yaml` sets this. That Render's balancer appends exactly one entry is an assumption to confirm against Render's docs and the logged `client` field after deploying.
- If the header has fewer entries than expected, fall back to the peer instead of guessing.

**Then we measured it on the live service, and the assumption was wrong.** After deploying with one trusted hop, I sent requests from one machine and watched `X-RateLimit-Remaining`: it went 29, 28, 27, 26, 25, then **back to 29**. My requests were landing in different buckets, so the rightmost entry wasn't my address but a Render/Cloudflare proxy address that changes between requests. Render's own feedback board confirms both halves of the problem: Render puts the client first but **doesn't strip** a client-supplied `X-Forwarded-For`, so neither end of that header can be trusted there.

The fix: Render sits behind **Cloudflare**, which **overwrites** `CF-Connecting-IP` with the real client address on every request, whatever the client sent. So `MINILANG_CLIENT_IP_HEADER=CF-Connecting-IP` names a header to trust; it wins when it holds a valid IP address (checked with `ipaddress`), and `render.yaml` sets hops back to 0, so nothing in `X-Forwarded-For` is trusted. If the header were ever missing, every such request would fall back to the proxy's address and share one bucket: too strict, but never bypassable.

The lesson is the most useful one in this project for an FDE role: **"the platform appends one entry" was a reasonable assumption, documented as an assumption, and it was false.** The only way to know was to test against the real deployment.

The same `client_ip()` helper feeds the rate limiter **and** the access log, so the log shows the IP that was actually charged. uvicorn itself runs with `--no-proxy-headers`, so it doesn't rewrite the address before our code sees it. (Worth knowing: uvicorn's default *does* trust `X-Forwarded-For` from `127.0.0.1`, so a bare local `uvicorn` run can be fooled from your own machine. Harmless locally, which is why the Dockerfile is explicit.)

## 6. Running untrusted code safely

Anyone on the internet can send a program, so the server must survive hostile ones:

| Threat | Protection |
|---|---|
| `while (true) {}` | The interpreter's step limit (200,000 statements, the playground's limit) ends it with a runtime error |
| Infinite recursion | The call-depth limit (500) |
| Printing forever | The output limit (2,000 lines) |
| A huge program | Body limit, declared or chunked (413), and source length limit (422) |
| Flooding requests | Rate limit (429), checked before the body is read |
| Many heavy programs at once | Concurrency gate: 4 at a time, then `503 server_busy` |
| Too many open connections | uvicorn `--limit-concurrency 64` (503) and `--timeout-keep-alive 5` |
| Escaping to the server | Not possible: MiniLang is interpreted from its AST, with no Python `exec`/`eval` and no file or network access |
| One slow request blocking others | Endpoints are plain `def`, so FastAPI runs them in a **thread pool** and the event loop keeps serving other requests |

**`def` vs `async def` in FastAPI.** An `async def` endpoint runs *on* the event loop, so CPU-bound work inside it (like compiling) blocks every other request. A plain `def` endpoint is run in a worker thread. Compiling is CPU work with nothing to `await`, so `def` is the right choice.

**Why a concurrency gate on top of the thread pool?** The pool has 40 threads, but Python's **GIL** lets only one thread run Python code at a time. Forty CPU-heavy programs don't run 40x faster; each just runs 40x slower, and every request (even `/health`) waits behind them. So the compiler endpoints take a slot from a `threading.BoundedSemaphore(4)` (`MINILANG_MAX_CONCURRENT_PROGRAMS`). The acquire is **non-blocking**: if all slots are taken the client gets `503 {"error": {"code": "server_busy"}}` with `Retry-After: 1` immediately, instead of queueing. A fast, honest "try again in a second" beats a request that hangs. The slot is released in a `finally`, so a crashing program can't leak it (there's a test for that).

### 6.1 The review that found real holes (and what it taught)

Before deploying, a review agent attacked the API and found that **the step limit wasn't enough**. Each of these programs runs only a few dozen steps:

| Attack (a few hundred bytes) | What happened before the fix |
|---|---|
| Double a string 40 times: `s = s + s` | Asked for a 17 TB string: the server was killed for running out of memory |
| Square an int 40 times: `x = x * x` | A number with trillions of digits: same memory blow-up |
| Build a 1 MB string, print it 2,000 times | A 2 GB JSON response (the output limit counted *lines*, not characters) |
| 9,000 nested parentheses | Python's `RecursionError` deep in the parser, so a `500` |
| `x / 3` on a 4,000-digit int | Python's `OverflowError`, so a `500` |

The lesson: **limit every resource, not just the obvious one.** Steps bound CPU time, but memory, output size and stack depth each needed their own limit. The fixes live in the compiler, so the CLI, the MCP server, the website and the API all get them:

- **Check before allocating** (`minilang/budget.py`). Before `a + b` on strings runs, the interpreter checks `len(a) + len(b)` against the string limit; before `a * b` on ints, it checks `a.bit_length() + b.bit_length()`. Checking *after* would be too late: the 17 TB string would already be on its way.
- **An allocation budget per run.** Every string or array the program creates is charged to a budget (50 million characters or array slots on shared servers). A program that keeps many medium-sized strings alive hits it even though no single string is too long.
- **Output counted in characters**, and values are measured before they're turned into text, so even a self-containing array (`push(xs, xs); print(xs);`) can't build an infinite string.
- **A wall-clock limit** (2 s on shared servers), checked every 1,024 steps, because reading the clock on every step would slow everything down.
- **A nesting cap in the parser.** More than 200 nested brackets, blocks or prefix operators, or an AST more than 400 levels deep (which catches `1 + 1 + 1 + ...`), is a syntax error. Real code nests a handful of levels.
- **A thread-safe recursion limit** (`minilang/recursion.py`). `sys.setrecursionlimit` is global to the whole Python process, not per thread. Two requests that each "raise it, then restore the old value" can interleave so that the raised value is never restored. Now the limit is shared: raised while any run needs it, restored when the last one finishes, behind a lock.

After the fixes, each attack ends with a clean `200 ok: false` and a message such as `string too long (131072 characters; limit 100000)`, in under 0.25 s. Running all of them used 88 MB at peak.

The bigger-picture answer, which is also the interview answer: these limits make a cooperative interpreter safe, but **the strongest isolation is a separate process** with OS limits (`RLIMIT_AS` for memory, a CPU-time limit, a kill on timeout), or a microVM. That's the next step if the API ever ran code in a language that *can* touch the system.

## 7. Observability

- **Request IDs.** Every response, **including 413, 429, 500 and 503**, has an `X-Request-ID`. If the caller sends one (for example from their own tracing), it's echoed back; otherwise a new one is generated. It's only accepted if it's short and plain, so it can't inject fake lines into the logs.
- **One JSON log line per request:** `{"request_id", "method", "path", "status", "ms", "client"}`, written in a `finally` so even a crash gets its line (with status 500). `client` is the resolved client IP (section 5). JSON lines can be searched and aggregated by log tools, unlike free text.
- **Crashes are logged with their request ID and traceback**, so a user reporting "request `abc123` failed" leads straight to the stack trace.
- **`/health`** lets Render (and Docker's `HEALTHCHECK`) restart the container if it stops answering. It sends `Cache-Control: no-store` so no cache in between can answer "ok" for a server that's down.

### The middleware order

Starlette wraps the app in each middleware you add, so the **last one added runs first**:

```
request ─► CORS ─► request ID / log / 500 ─► rate limit ─► body limit ─► FastAPI routes
```

- **CORS outermost**, so every response (413, 429, 500, 503) gets `Access-Control-Allow-Origin` and the showcase site's JavaScript can read the error instead of seeing an opaque network failure.
- **Request ID next**, so it stamps every response produced further in, and catches exceptions from everything inside it.
- **Rate limit before body limit**, so a throttled client is refused before we read a single byte of its body.

## 8. Docker and deployment

The `Dockerfile`:
- starts from a **pinned** `python:3.12.15-slim` (small image; a fixed patch version so rebuilds are reproducible, bumped deliberately for security fixes);
- copies **only** what the API needs (the package, `pyproject.toml`, the spec); `.dockerignore` excludes everything else, including `.env`, so secrets can't end up in the image;
- runs as a **non-root user**, so a hypothetical escape would get a powerless account;
- has a `HEALTHCHECK` that calls `/health`;
- reads `$PORT`, which Render sets;
- runs uvicorn with `--no-proxy-headers` (our code decides which forwarded IP to trust), `--workers 1` (the limiter and gate are per process), `--limit-concurrency 64`, `--timeout-keep-alive 5` and `--no-server-header` (don't advertise the server version).

The app also reads the language spec **once in `create_app`**, so a missing spec file stops the server at startup (a failed deploy you notice) instead of turning every `/v1/spec` request into a 500 (an outage you might not).

`render.yaml` is a **Render Blueprint**: infrastructure as code. Render reads it and creates the web service (Docker runtime, free plan, health check path, environment variables including `MINILANG_CLIENT_IP_HEADER=CF-Connecting-IP`, auto-deploy from `branch: main`). The free plan sleeps after 15 minutes without traffic, so the first request after that takes about 30–50 seconds while the container starts (a **cold start**).

**CI** builds the image on every PR, runs the container and calls `/health`, `/v1/run` and `/v1/spec`. It then checks the hardening against the real image: the container's user ID isn't 0 (root), a 200 KB body gets `413` both with `Content-Length` and chunked, and an unknown route gets the `404` error format. A broken Dockerfile can't be merged, even though Docker isn't installed on the development Mac.

## 9. Testing

84 API tests, about 99% coverage of `minilang/api/`, using FastAPI's `TestClient` (it calls the app in-process; no server or network needed):
- every endpoint's success and failure shapes;
- validation: missing field, empty source, wrong type, an extra field, too long (422), body too big (413), unknown route (404 in the error format);
- **streamed bodies:** a chunked body over the limit is a `413` (the test asserts there really was no `Content-Length`); the middleware is also driven directly with fake ASGI messages to prove it stops reading after the chunk that crosses the limit and that a small body is replayed intact;
- rate limiting: the third request with a limit of 2 is a `429` with `Retry-After`; a throttled request with broken JSON is still a `429` (proof the body wasn't parsed); health, spec, docs and the OpenAPI schema aren't limited;
- **client IP:** a spoofed `X-Forwarded-For` doesn't get a fresh bucket; with one trusted hop the rightmost entry is the client; a short header falls back to the peer; the access log records the resolved IP;
- **concurrency gate:** with the app's semaphore held, `/v1/run` answers `503 server_busy` with `Retry-After: 1`; a crashing program still releases its slot;
- **500s:** a forced internal error returns a generic body, keeps `X-Request-ID` and the CORS header, and is logged with its request ID and still gets an access-log line with status 500;
- OpenAPI: `source` has `maxLength` 20,000, every route has a summary and operation ID, 500/503 are documented, `/v1/compile` still shows `CompileResponse`;
- startup: a missing spec file makes `create_app` raise;
- CORS: the showcase site's origin is allowed and others are not;
- the token bucket with a fake clock: bursts, refill, capacity cap, `Retry-After` math, separate clients, LRU eviction;
- settings from environment variables, including rejecting invalid values at startup (negative hops, zero slots, a source limit above the schema's).

The full suite is now 610 tests.

## 10. Key terms

| Term | Meaning |
|---|---|
| **REST** | Resources over HTTP, with methods (GET/POST) and status codes carrying meaning |
| **ASGI** | The async interface between Python web apps and servers (uvicorn runs FastAPI over it) |
| **Event loop / thread pool** | One loop handles many connections; blocking work goes to worker threads |
| **Pydantic** | Data validation from type hints; FastAPI uses it for requests, responses and docs |
| **OpenAPI** | A standard description of an HTTP API; generates docs and client code |
| **Token bucket** | A rate-limiting algorithm: tokens refill at a fixed rate, each request spends one |
| **429 / Retry-After** | "Too many requests" plus how long to wait |
| **413** | "Payload too large" |
| **CORS** | Browser rules for which websites may call an API from JavaScript |
| **X-Forwarded-For** | The header each proxy appends the client's IP to; only the entries your own proxies add are trustworthy |
| **Chunked encoding** | Sending a body in pieces without declaring its size first |
| **Pure ASGI middleware** | A class wrapping the app at the `scope, receive, send` level; sees every message, including the body as it arrives |
| **Semaphore / 503** | A counter of free slots; "server busy, retry later" when none are free |
| **GIL** | Python's global interpreter lock: one thread runs Python code at a time |
| **Cold start** | The delay while a sleeping container starts up |
| **Infrastructure as code** | Describing servers in a file (`render.yaml`) instead of clicking through a dashboard |

## 11. Interview questions and answers

**Q: Tell me about a serious bug you found before shipping.**
Before deploying the API, I had a review attack it. A 130-byte program that doubled a string 40 times asked for a 17 TB string and got the server killed for running out of memory. Squaring an integer 40 times did the same, and 9,000 nested parentheses crashed the parser with a 500. My step limit stopped infinite loops but nothing else, so I added a limit for each resource: sizes are checked *before* a string or integer is built, every allocation is charged to a per-run budget, output is counted in characters, there's a wall-clock limit, and the parser caps nesting depth. I also found the recursion limit was being raised and restored per request on a process-global setting, which raced between threads, so I made it reference-counted behind a lock. Every attack now returns a clean error in under a quarter of a second. The lesson: limit every resource a program can consume, not just the obvious one.

**Q: Why is a syntax error in the submitted program a 200 and not a 400?**
Because the request was valid and the server did its job: it compiled the program and is reporting the result. A 400 would mean the API call itself was malformed. Keeping them apart lets a client tell "my integration is broken" from "the user's code has a bug".

**Q: How does your rate limiter work, and what breaks at scale?**
A token bucket per client IP: 30 tokens, refilling at 30 per minute, one per request, 429 with Retry-After when empty. It's in memory, thread-safe with a lock, and bounded by LRU eviction. It runs as ASGI middleware, so a throttled request is refused before its body is parsed. With more than one server (or worker) the counts would be per instance, so I'd move it to Redis with an atomic operation.

**Q: Behind a load balancer, how do you get the real client IP? Can a client fake it?**
It depends on the platform, so I measured it. The client can put anything in `X-Forwarded-For` before it reaches the balancer, so the leftmost entry is attacker-controlled; my first version trusted it, and a new fake value meant a new rate-limit bucket. My second version counted from the right, assuming Render appends exactly one entry. On the live service the rate-limit counter reset between my own requests, so the rightmost entry was a changing proxy address. The final version trusts `CF-Connecting-IP`, which Cloudflare (in front of Render) overwrites with the real client address, validates it as an IP, and trusts nothing in `X-Forwarded-For`. One helper decides the client for both the rate limiter and the logs, and uvicorn is told not to rewrite the address itself.

**Q: How do you stop someone uploading a huge body if they don't send Content-Length?**
With chunked transfer encoding there's no size up front, so checking the header isn't enough. An ASGI middleware reads the body chunk by chunk, counts bytes, and sends a 413 as soon as the count passes the limit, without reading the rest. If the body fits, it replays the buffered bytes to the app.

**Q: Your API runs code from strangers. How is that safe?**
The language is interpreted from its AST with no access to Python, files or the network, so there's nothing to escape to. The interpreter has step, recursion and output limits; requests have size limits; clients have a rate limit; only 4 programs run at once; the container runs as a non-root user. If I needed to run arbitrary Python, I'd use stronger isolation: a separate sandboxed process or a microVM such as gVisor or Firecracker, with a CPU-time limit.

**Q: Why `def` instead of `async def` for the endpoints, and why limit concurrency on top?**
Compiling is CPU-bound and has nothing to await. Inside `async def` it would block the event loop and stall every other request. With `def`, FastAPI runs it in a thread pool. But because of the GIL, 40 threads compiling at once just share one core and all get slower, so a non-blocking semaphore allows 4 programs at a time and answers `503 server_busy` with `Retry-After: 1` beyond that. Failing fast is kinder to clients than an unbounded queue.

**Q: A browser user reports "the API just says network error" when the server crashes. Why?**
Because the 500 had no CORS headers: it was produced by Starlette's outermost error layer, outside the CORS middleware, so the browser hid the response from the page. I moved the exception handling into my own middleware, which sits inside CORS, so the 500 gets `Access-Control-Allow-Origin`, an `X-Request-ID` and a log line with the traceback.

**Q: How do you know the Docker image works if you don't have Docker locally?**
CI builds it on every pull request, starts the container, waits for `/health`, calls the real endpoints with curl, and checks the hardening: non-root user, 413 for both declared and chunked large bodies, the 404 error format. The image is tested exactly as it will run in production.
