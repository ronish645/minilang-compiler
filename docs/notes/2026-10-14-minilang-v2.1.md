The project got a written review ("update_compiler" in Google Docs). Today we **checked each claim against the code** and then fixed the language-level issues that were real. These notes cover how we triaged the review, the three changes and how each one works, and how to talk about them in an interview.

## 1. Triage: verify before you act

A review is a list of claims, not a list of tasks. Before writing any code we reproduced each claim with a small program or a `grep`:

| Claim in the review | Verified? | Decision |
|---|---|---|
| Calls only parse when the callee is a name, so `makeAdder(5)(10)` and `fs[0]()` fail | ✅ syntax error `expected ')' but found '('` | **Fixed today** |
| `let x;` then `x = 10` in `if` and `x = "hello"` in `else` is rejected | ✅ `cannot assign string to 'x' of type int` | **Fixed today** |
| Very few built-ins (no `abs`/`min`/`max`/`ord`/`chr`/slicing) | ✅ | **Fixed today** |
| AST nodes are generic, children are read by position | ✅ `children[...]` appears 65 times | Roadmap (big refactor, no user-visible change) |
| TAC is generated but never executed | ✅ | Roadmap (TAC VM) |
| Benchmark has a ceiling/floor problem | ✅ already in `bench/README.md` | Mid-size model skipped for now; documented as a limitation |
| `(fn(x) {...})(5)` fails because of the parser | ❌ MiniLang has **no anonymous functions** at all; this is a missing feature, not a parser bug | Not done (named functions passed by value cover the use case) |

We also found a problem **the review missed**: `fn apply(f, x) { return f(x); }` was rejected with `'f' is not a declared function`. The type checker only accepted calls on names declared with `fn`, so functions could be passed around but never called through a parameter or variable. The spec even said "Functions are **not** values". Fixing the parser alone would not have made functions first-class.

> **Lesson:** reproduce every claim yourself. One claim was wrong, and the biggest real problem was next to one the review found but not the same one. FDE and Solutions Engineers get the same kind of input from customers: bug reports that are partly right.

## 2. Change 1: calls on any expression (first-class functions)

### 2.1 Parser: a call is a postfix operator

Before, `primary()` handled calls, and only for an identifier:

```python
# before (primary)
if tok.type == "IDENT":
    node = make_node("Identifier", tok, value=tok.value)
    if self.match("SEP", "("):
        return self.call_arguments(node)  # only name(...) is a call
    return node
```

Now `postfix()` handles calls in the same loop as indexing `[...]` and `++`/`--`:

```python
def postfix(self) -> ASTNode:
    node = self.primary()
    while True:
        if self.match("SEP", "("):
            node = self.call_arguments(node)  # f(x), f(x)(y), fs[0](x)
        elif self.check("SEP", "["):
            ...  # xs[i], f()[0]
        elif self.check_op(POSTFIX_OPS):
            ...  # x++
        else:
            return node
```

**Why a loop?** Postfix operators chain left to right: `makeAdder(5)(10)[0]` is `((makeAdder(5))(10))[0]`. Each pass wraps the node built so far, so the loop yields exactly that nesting. This is how C, JavaScript and Python grammars treat calls (`postfix-expression ( arguments )` in the C grammar).

### 2.2 Type checker: three kinds of callee

```python
def visit_Call(self, node):
    callee, args_node = node.children
    if callee is a built-in name:     -> check_builtin(...)        # static arg types
    elif callee is an Identifier:     -> check_named_callee(...)   # see below
    else:                             # fs[0], makeAdder(5), ...
        callee_type = self.analyze(callee)
        if callee_type not in ("function", UNKNOWN):
            raise SemanticError(f"cannot call a value of type {callee_type}")
```

`check_named_callee` handles a name:
- **Declared with `fn`:** arity is known, so a wrong argument count is a **compile-time** error (as before).
- **A variable or parameter:** fine if its type is `function`, `unknown` or `null`. Arity is checked **at run time**, because the checker doesn't know which function it will hold. This is gradual typing, the same rule MiniLang already used for parameters and array elements.
- **Anything else** (`let x = 5; x(1);`): `cannot call a value of type int`, a better message than the old `not a declared function`.
- **Unknown name:** still `'sqare' is not a declared function` with the `did you mean 'square'?` hint.

### 2.3 Runtime and codegen

- **Runtime:** evaluate the callee expression first, then the arguments (left to right, like JavaScript), then check that the result is a `UserFunction`. Closures already worked, because `UserFunction` stores the environment it was defined in. That's why `makeAdder(5)(10)` and a stateful `counter()` worked without other changes.
- **Codegen:** a named call is unchanged (`t2 = call sq, 1`). Any other callee is computed into a temp first:

```
fs[0](7);   =>   t1 = fs[0]
                 param 7
                 t2 = call t1, 1
```

Built-ins are deliberately **not** values (`let f = len;` is an error). They're checked by a separate static table, and making them values would need a second representation for no current use case (YAGNI).

## 3. Change 2: joining types across `if` / `else`

### 3.1 The bug

MiniLang fixes a variable's type at its first assignment. The checker walks the AST in source order, so for

```js
let x;
if (flag) { x = 10; } else { x = "hello"; }
```

it saw `x = 10` first, set `x` to `int`, and then rejected the `else` branch. But **only one branch ever runs**: the `else` branch can never see the assignment in the `if` branch. The checker was following the order of the *text*, not of the *control flow*.

### 3.2 The fix: check each branch from the same starting point, then join

```python
def visit_If(self, node):
    self.require_bool_condition(node.children[0], "if")
    untyped = [s for s in visible symbols if s.var_type in OPEN_TYPES]   # unknown / null
    before = [s.var_type for s in untyped]
    outcomes = []
    for branch in node.children[1:]:
        try:
            self.analyze(branch)
        finally:
            outcomes.append([s.var_type for s in untyped])   # what this branch did
            restore every symbol to `before`                  # next branch starts fresh
    for symbol, start, *results in zip(untyped, before, *outcomes):
        symbol.var_type = join_types(start, results)
```

```python
def join_types(start, branch_types):
    settled = {t for t in branch_types if t not in OPEN_TYPES}
    if not settled:
        return start  # no branch gave it a type
    return settled.pop() if len(settled) == 1 else UNKNOWN
```

| Branches | Result | Why |
|---|---|---|
| `int` / `int` | `int` | They agree, so we keep static checking |
| `int` / `string` | `unknown` | Could be either, so it's checked at run time (gradual typing) |
| `int` / no `else` | `int` | Same as before the change, so no existing program breaks |
| `else if` chains | recursive | An `else if` is an `If` node inside the `else`, so it joins its own branches first |

Only **open** variables (declared without a value, or holding `null`) take part. A variable that already has a type is checked in every branch exactly as before. A `try/finally` makes sure the types are restored even if a branch raises an error.

### 3.3 The compiler theory behind it

This is a small version of what an optimizing compiler does with **SSA form** (static single assignment). Where two control-flow paths meet, a **φ (phi) node** merges the values from each path: `x3 = φ(x1, x2)`. Our `join_types` is the type-level version of φ. It's also the **join** in dataflow analysis (the least upper bound in a lattice): `int ⊔ int = int`, `int ⊔ string = unknown`, where `unknown` is the top of the lattice.

**Design alternative we didn't pick:** reject branches that disagree ("x is int in one branch and string in the other"). That's stricter and fits "a variable's type is fixed", but MiniLang already lets parameters be `unknown`, so making `x` dynamic is the consistent choice. Union types (`int | string`) would be more precise, but they need a real type system (YAGNI for now).

**Known limitation:** loops aren't joined. An assignment inside a `while` body still fixes the type for the code after the loop, because a correct loop join needs a **fixed-point iteration** (re-check the body until the types stop changing). It's a natural next step if it ever matters.

## 4. Change 3: six new built-ins

| Built-in | Static result type | Runtime rules |
|---|---|---|
| `abs(x)` | same as `x` | int or float only (`abs(true)` is an error) |
| `min(a, b)`, `max(a, b)` | `int`, or `float` if either is a float | `max(2, 1.5)` returns `2.0`, so the runtime value matches the static type |
| `ord(c)` | `int` | exactly one character |
| `chr(n)` | `string` | `0 <= n <= 0x10FFFF` |
| `slice(x, start, end)` | same as `x` | `0 <= start <= end <= len(x)`; returns a **copy** |

### 4.1 Result types that depend on the arguments

Before, every built-in had one fixed result type (`"len": "int"`). `max(1, 2)` should be `int` but `max(1, 2.0)` should be `float`, so a result can now be a **rule function**:

```python
RESULT_TYPES = {
    "len": "int",
    "max": numeric_result,      # int, or float if any argument is a float
    "slice": same_as_first,     # array -> array, string -> string
    ...
}
result = RESULT_TYPES[name]
return result(arg_types) if callable(result) else result
```

`ARITY` and `BUILTIN_NAMES` are now **derived** from `EXPECTED_TYPES` instead of written out by hand, so adding a built-in means editing one table plus its implementation. That's the single-source-of-truth idea from v2, taken one step further.

### 4.2 Not letting Python leak in (again)

The implementations are thin wrappers over Python, but Python's behaviour isn't always MiniLang's:

- `"abc"[0:10]` in Python silently clamps to `"abc"`, and `xs[-1:]` counts from the end. MiniLang's `slice` **raises an error** for any out-of-range or negative bound. Same rule as `xs[-1]` in v2.
- Python's `min(1, 2.0)` returns `1` (an int). The static checker says `float`, so the runtime wrapper converts the result to keep the two consistent.
- `True` is an `int` in Python, so `abs(True)` is `1`. MiniLang checks argument types with `type_name()`, which reports `bool`, so it's rejected.

### 4.3 Hints

The fix-it hints now know about the new built-ins: `Math.max(1, 2)` gives *"there is no Math object; use abs(x), min(a, b), max(a, b)"*, and `s[0:2]` or `substring(...)` gives *"use slice(x, start, end)"*.

## 6. The benchmark

The spec is the benchmark's system prompt, so changing the language changes the experiment. The runner's cache key includes the full system prompt, so the change automatically invalidated the cached episodes. We re-ran the four hosted models on tier 5 (`--run-name v21-tier5`), then ran the local Qwen model on the same run afterwards (one worker, so the Mac stays cool). The hosted episodes came from the cache, so they cost nothing the second time.

### Results

Run `v21-tier5`: 5 models × 10 tier-5 tasks × 5 conditions = 250 episodes. The hosted models passed **200 of 200** for about **$0.75**, and the local Qwen model passed **2 of 50**. Full tables: [`bench/results/v21-tier5/REPORT.md`](../../bench/results/v21-tier5/REPORT.md).

| Model | Pass | Tested before submitting | Cost per solve |
|---|---|---|---|
| Claude Haiku 5.5 | 50/50 | 100% | $0.0007 |
| Claude Sonnet 5.5 | 50/50 | 50% | $0.0093 |
| GPT-6 Luna | 50/50 | 100% | $0.0003 |
| GPT-6.1 Sol | 50/50 | 100% | $0.0047 |
| Qwen 2.5 3B (local, 16K context) | 2/50 | 42% | free |

What it tells us:

1. **The new spec didn't confuse anyone.** All four models stayed at 100%, so the v2.1 additions read clearly enough to learn in context.
2. **Models used the new built-ins, but not everywhere.** 33 of 200 programs called one: `ord` in anagram counting (19) and Caesar shifts (10, with `chr`), and `slice` in `reverse_words` (4). Half the Caesar solutions still built a lookup table, so models often fall back on the long way even when the spec offers a shortcut.
3. **The ceiling is still the ceiling.** Every first run passed, so there was nothing to repair and the feedback conditions couldn't differ. That's the review's main point about the benchmark: it needs mid-size models or bigger tasks, not more language features.
4. **Qwen 3B stayed at the floor, even with the whole spec in context.** The 16K window fixed the truncation, but its score didn't improve. It wrote no code at all in 17 of 50 episodes, and the most common compile error was `expected ';' but found '.'`, which comes from calling methods like `xs.length` that MiniLang doesn't have. Both passes were bubble sort and worked on the first run, so it **repaired nothing** in any condition, including `hint`. It ran its code in only 17 of 40 tool episodes, and even fix-it hints can't help a model that doesn't run its code and act on the feedback.
5. **Together, this is the ceiling/floor problem in one table.** Hosted models never fail, Qwen 3B almost never succeeds, and neither group gives the feedback conditions anything to measure. The next useful experiment is a model in between (7–32B), as the review said.
6. **Sonnet's testing habit repeated.** It ran its code before submitting in only half its tool episodes, the same pattern as the v2 run. This time every untested submission happened to be correct.

## 7. Key terms

| Term | Meaning |
|---|---|
| **First-class function** | A function that is a value: it can be stored, passed, returned and called from any expression |
| **Postfix expression** | An operator written after its operand: `f(x)`, `xs[i]`, `x++`. They chain left to right |
| **Callee** | The expression being called: in `fs[0](3)` it's `fs[0]` |
| **Closure** | A function plus the environment it was created in (`add` remembers `n` in `makeAdder`) |
| **Control-flow merge / join point** | Where branches meet again, e.g. after an `if`/`else` |
| **φ (phi) node** | In SSA form, a node that picks a value depending on which path was taken |
| **Lattice / least upper bound (join)** | An ordering of types where `unknown` is above everything; a join takes the smallest type that covers both inputs |
| **Fixed-point iteration** | Re-running an analysis until nothing changes; needed to join types correctly across loops |
| **Gradual typing** | Check what's known statically, defer the rest to run time |

## 8. Interview questions and answers

**Q: Someone gave you a code review with a dozen suggestions. How did you decide what to do?**
I reproduced each claim first, with a small program or a grep. One claim was wrong (anonymous functions don't exist in the language, so that wasn't a parser bug), and while reproducing another I found a bigger problem the review missed: the type checker didn't let you call a function through a variable. Then I ranked what was left by user impact and cost. Bug fixes and small features went in before the merge, and refactors with no user-visible change (typed AST, TAC VM) went on the roadmap.

**Q: Why was `makeAdder(5)(10)` a syntax error, and how did you fix it?**
Calls were parsed in `primary()` and only after an identifier. A call is really a postfix operator, like indexing, so I moved it into the `postfix()` loop. Each iteration wraps the expression built so far, so chained calls and indexing nest left to right. Then the type checker had to accept any callee whose type is `function` or `unknown`, and the runtime had to evaluate the callee as an expression.

**Q: How does your type checker handle a variable assigned different types in an if/else?**
It checks each branch from the types that were known before the `if`, records what each branch ended with, and joins them where the branches meet. If they agree, the type stays static. If they disagree, the variable becomes `unknown` and is checked at run time. It's the type-level version of a φ node in SSA, or a join in a dataflow lattice.

**Q: What about loops?**
Not joined yet. A loop body can run many times, so a correct analysis has to iterate to a fixed point. The current behaviour is unchanged from before and documented as a limitation.

**Q: Why is arity checked at compile time for `sq(1, 2)` but at run time for `g(1, 2)`?**
For `sq`, the checker knows exactly which function is called. `g` is a variable that could hold any function, so the arity is only known at run time. That's the same gradual-typing trade-off MiniLang already makes for parameters.

**Q: Why did `min(1, 2.0)` need a wrapper?**
Python returns `1`, an int, but the checker says the result is `float`. If the runtime and the checker disagree, a program that type-checks can still crash. The wrapper keeps them consistent.
