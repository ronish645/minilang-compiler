# MiniLang v2: Build Notes

**Date:** 2026-10-09 · **Author:** Ronish Shrestha · **Branch:** `feat/language-v2` · **Previous notes:** [2026-10-08](2026-10-08-minilang-upgrade.md)

Yesterday's benchmark showed that frontier models learned MiniLang v1 almost perfectly from its spec, so the error-message experiment had nothing to measure. Today we made the language **strong enough to write real programs** and the compiler **smart enough to explain mistakes**, then tested models on harder programs. These notes explain what changed, how it works, why, and how to talk about it.

---

## 1. Why v2

| Problem found yesterday | What v2 does about it |
|---|---|
| No arrays or string operations, so every task had to be tiny, and tiny tasks don't make strong models fail | Arrays, string indexing and built-ins make real programs possible: sorting, searching, parsing, matrices |
| Some "features" were really design flaws (`&&` always ran both sides; functions had to be declared before use) | Fixed: short-circuit logic and function hoisting |
| Errors said *what* was wrong, but not *how to fix it* | Fix-it hints that recognize habits from other languages |
| The compiler stopped at the first error | It reports every independent error in one run |

Engineering lesson: **the eval drove the product changes.** The benchmark's weak spots told us what the language and compiler needed.

## 2. Language features added

### 2.1 Arrays

```js
let xs = [3, 1, 2];
xs[0] = 9;         // index assignment
xs[1]++;           // ++ / -- / += work on elements
push(xs, 4);       // append
let last = pop(xs);
let grid = [[1, 2], [3, 4]];
grid[1][0] = 7;    // nested indexing
```

**How it's built, stage by stage:**

| Stage | Change |
|---|---|
| Lexer | Nothing: `[` and `]` were already separator tokens |
| Parser | `[a, b]` becomes an `ArrayLiteral` node (in `primary`); `xs[i]` becomes an `Index` node (in `postfix`, so `a[i][j]` and `f(x)[0]` chain naturally) |
| Semantic | New type `array`; indexing an array gives `unknown` (elements can be anything), indexing a string gives `string`; the index must be an int |
| Runtime | Arrays are Python lists. `values.get_index` / `set_index` check bounds and **reject negative indexes**, which Python would silently accept (`xs[-1]` is the last element in Python) |
| Codegen | `t1 = newarray 3`, `t1[0] = 5`, `t2 = xs[i]` |

**Design decisions worth knowing:**

- **Reference semantics:** `let b = a;` shares the array, like JavaScript and Python. A function can fill an array it receives. Value semantics would be more surprising to programmers.
- **`==` compares contents** (`[1, 2] == [1, 2]` is `true`), unlike JavaScript (which compares identity). That's simpler to explain and test, and it's what the anagram task relies on.
- **Strings inside arrays print quoted**, `["a", 1]`, so `["1"]` and `[1]` don't look the same.

### 2.2 The `place()` abstraction (getter/setter pairs)

Assignment now has two kinds of target: a variable (`x = 1`) or an element (`xs[i] = 1`). Instead of duplicating every assignment form (`=`, `+=`, `++x`, `x++`) for both, the interpreter turns any target into a **getter/setter pair**:

```python
def place(self, target, env):
    if target.kind == "Index":
        container = self.eval_expr(target.children[0], env)
        index = self.eval_expr(target.children[1], env)
        return (lambda: get_index(container, index)), (lambda v: set_index(container, index, v))
    name = target.value
    return (lambda: env.resolve(name).value), (lambda v: env.assign(name, v))
```

`xs[f()] += 1` then evaluates `xs` and `f()` **exactly once**: read via the getter, write via the setter. A naive version would evaluate `xs[f()]` twice and call `f` twice. This is the same idea as an "lvalue" in C compilers.

### 2.3 Built-in functions and a shared contract

`len`, `push`, `pop`, `str`, `int` live in `minilang/builtins.py`, which holds **both** the compile-time type rules (`check_builtin`) and the runtime implementations (`call_builtin`), driven by the same `EXPECTED_TYPES` table. Keeping both in one place means the type checker and the interpreter can't disagree.

Gradual typing matters here: `len(5)` is rejected **before running**, but `fn f(x) { return len(x); } f(5);` can only be caught **at run time**, because `x` is `unknown`. Both produce the same message.

`int(x)` was chosen as the answer to "integer division", instead of adding a `//` operator: `int(7 / 2)` is `3`, truncating toward zero like C and Java. It also converts strings (`int("42")`), so one built-in covers two needs.

### 2.4 `break` and `continue`

They're implemented as **exceptions**, just like `return`:

```python
def run_loop_body(self, body, env):
    try:
        self.exec_stmt(body, env)
    except BreakSignal:
        return False  # stop the loop
    except ContinueSignal:
        pass  # fall through: a for-loop still runs its update
    return True
```

The semantic analyzer tracks `loop_depth` and resets it to 0 inside a function body, so `while (true) { fn f() { break; } }` is rejected: `break` can't jump out of a function.

In the code generator, a stack of `LoopLabels` gives each loop its jump targets. A `for` loop's `continue` label (just before the update) is **only allocated if a `continue` is used**, so existing programs' three-address code didn't change and their golden tests kept passing.

### 2.5 Short-circuit `&&` / `||`

In v1, `b != 0 && a / b > 2` crashed when `b` was 0, because both sides always ran. Now the runtime returns early, and the code generator emits jumps:

```
t8 = flag
if_false t8 goto SC_END9   // left is false → skip the right side
t9 = !false
t8 = t9
label SC_END9
```

This was the only intended change to the golden snapshots. We **diffed the snapshot before accepting it**: only the `&&`/`||` lines changed, and the program output was identical.

### 2.6 Hoisting (mutual recursion)

Before analyzing (or running) a block, both the semantic analyzer and the interpreter first declare every function in that block. So `isEven` can call `isOdd` even though `isOdd` is written below it. Variables are **not** hoisted; only functions are, as in JavaScript's function declarations.

## 3. Compiler diagnostics

### 3.1 Fix-it hints (`minilang/hints.py`)

Most mistakes in a new language are **habits from an old one**. The hints module recognizes them:

| You write | Hint |
|---|---|
| `xs.length` | MiniLang has no methods or properties; built-ins are len(x), push(xs, v), ... |
| `var x = 1` | declare variables with let (or const) |
| `True`, `None` | booleans are lowercase / the empty value is null |
| `a ? b : c` | MiniLang has no ternary operator; use if / else |
| `for i in xs` | use a C-style loop: for (let i = 0; i < len(xs); i++) |
| `"n=" + n` | convert numbers to text with str(n) |
| `n = n / 2` (n is an int) | '/' always produces a float; for integer division use int(a / b) |
| `print(totl)` | did you mean 'total'? |

"Did you mean" uses Python's `difflib.get_close_matches`, which measures string similarity, against every name visible in scope plus the built-ins.

Hints live on the error object (`error.hint`), print as a `= help:` line, and appear in JSON as `"hint"`.

### 3.2 Reporting every error

- **Semantic:** `analyze_statements()` wraps each statement in `try/except`, records the error in an `ErrorCollector` (capped at 10), and continues. At the end it raises the **first** error, with the rest attached as `error.additional`. The public API didn't change: callers still catch one exception.
- **Avoiding cascades:** if `let x = missing;` fails, `x` is still declared (as `unknown`), so later lines using `x` don't each produce a bogus "x is undeclared" error.

### 3.3 Parser error recovery: a debugging story

The first version used the textbook approach, "panic mode": after an error, skip tokens until the next `;`. A demo with `scores.length` inside a `for (...)` header produced **3 errors for 1 mistake**. The skip stopped at the `;` *inside* the for-header, and the leftovers (`i++) {`) looked like new broken statements.

The fix: **rewind to the start of the failed statement and skip all of it, counting brackets.** The statement ends at a `;` outside any brackets, or after the `}` that closes its body (continuing through `else`). A `}` that closes an *outer* block is left alone. We wrote the failing test first (`TestRecoveryQuality`), then the fix. Result: one mistake, one error.

**Interview lesson:** the textbook algorithm passed the simple tests; a realistic example exposed it. Always try your feature on messy, real input.

## 5. Key terms (new today)

| Term | Meaning |
|---|---|
| Reference semantics | Assigning or passing an array shares it rather than copying it |
| lvalue / place | Something that can be assigned to (a variable or an element), as opposed to a plain value |
| Short-circuit evaluation | The right operand of `&&`/`\|\|` only runs if it can change the result |
| Hoisting | Declaring functions before running a block, so call order doesn't matter |
| Panic-mode recovery | After a syntax error, skip input to a safe point and keep parsing |
| Cascading errors | Bogus follow-on errors caused by an earlier one |
| Fix-it hint | A suggested correction attached to an error |
| Edit distance / similarity | How alike two strings are; powers "did you mean" |

## 6. Interview questions and answers

1. **How did you add arrays to a compiler?** Every stage changed: the parser gained `ArrayLiteral` and `Index` nodes, the type checker gained an `array` type and index rules, the interpreter got bounds-checked list access, and the code generator emitted `newarray` and indexed loads and stores. I wrote end-to-end tests first.

2. **Why reject `xs[-1]` when Python allows it?** The interpreter is written in Python, but MiniLang has its own semantics. Silently inheriting Python's negative indexing would be a "leaky abstraction", the same family of bug as `True == 1`, which I fixed in v1.

3. **How do `break` and `continue` work in your interpreter?** As exceptions caught by the loop, the same way `return` unwinds a function. `continue` still runs a for-loop's update. The type checker rejects them outside loops, including across function boundaries.

4. **Why did you change `&&` to short-circuit, and how did you verify it didn't break anything?** The old behavior made `b != 0 && a / b > 2` crash, which is a design flaw. The golden snapshot for one program changed, and I diffed it before accepting: only the `&&`/`||` lowering changed, and the output was identical.

5. **How do you report multiple errors without cascades?** Statement-level recovery: semantic errors are collected per statement, failed declarations still declare their variable, and the parser skips the whole broken statement using bracket depth. I found the cascade problem by testing a realistic broken program, not a toy one.

6. **Why put fix-it hints in a compiler that's used by AI models?** Small models fail mostly by copying habits from JavaScript or Python. A hint that names the habit ("use len(xs)") is direct, actionable feedback. That's the hypothesis the new `hint` condition tests.

7. **What is the `place()` pattern?** It turns an assignable target into a getter and a setter, so every assignment form works on both variables and array elements, and the target expression is evaluated exactly once.

8. **How did you keep the type checker and interpreter consistent for built-ins?** One table of expected argument types drives both the static check and the runtime check, in one module.
